# Deadbeat invoice-chasing app, standup rule-pack and FR9 kill switch (v1)

Adds `apps/deadbeat`, a Next.js app that drives the unmodified engine from daily `tick` events and sends reminders to an in-app outbox only. Adds `packs/standup`, three `.curse` files with a `simulate()` dry run, and an FR9 kill switch (`CURSE_ENGINE_ENABLED`, `host.setEngineEnabled`) enforced at event intake in both Deadbeat and GrimMod, answering 503 on `POST /api/events`. `packages/curse-engine` and `docs/` have no changes in the diff, there is no real email, database or network use, and prose has no em dashes. `pnpm test` is green for the apps I ran.

Watch for: (1) a multi-day advance that is interrupted by the kill switch leaves invoices partly advanced (likely); (2) the programmatic override is silently dropped by `/api/reset` and `/api/fixtures` (confirmed); (3) the simulate route hard-codes the declared capability set (possible drift).

**Verdict**: APPROVED

## High-level view

Deadbeat splits cleanly into an adapter that only writes to memory, a host that owns the clock and per-invoice tier tracking, and a grimoire whose undo marks outbox entries retracted instead of deleting them. The engine executor does no dedupe, so the host hides curses that have already acted on an invoice; this is the load-bearing piece and it is tested.

The standup pack is data plus one test. Its three curses use only `post` and `escalate`, and the test asserts exact event ids for each curse over a fixed week of fixtures, so reverting a curse would fail it.

The kill switch is a single refusal at intake, checked before any state moves, with the env var read on every call so it can be flipped without a restart. Undo and reads stay available while off. The edges are the mid-run case and the lifetime of the programmatic override.

<summary>Issues (5)</summary>

1. **Partial advance on mid-run disable (likely)**: `intake` throws inside the day loop in `advanceClock`, after the clock and every invoice's `daysOverdue` were incremented for that round. Check the switch once per round before the increment, or snapshot and roll back on `EngineDisabledError`.
2. **Override lost on reset (confirmed)**: `resetHost` and `refreshFixtures` build a new host with no override, so `setEngineEnabled(false)` is silently undone by `POST /api/reset` or `/api/fixtures`. Carry the override across, or document that only the env var survives.
3. **Hard-coded declared set in simulate (possible)**: `simulate/route.ts` passes `["email","escalate"]` instead of deriving it from the adapter, so adding a capability to the adapter will not change dry runs. Derive it from the adapter.
4. **Kill switch copy-pasted across hosts (confirmed)**: `ENGINE_ENABLED_ENV`, `engineEnabledFromEnv` and `EngineDisabledError` are duplicated in both `host.ts` files and can drift. Consider sharing them, outside `packages/curse-engine`.
5. **Untested kill-switch edges (confirmed)**: nothing covers simulate while off, a flip during a multi-day advance, or reset while overridden. Add tests alongside fixes 1 and 2.

<summary>Details</summary>

## Kill switch: single intake choke point, with a mid-run gap

`advanceClock` validates `days` and then checks the switch before moving the clock, and `intake` checks it again for each event. The first check keeps a disabled call from changing anything. The second is the one that matters for a long request: with `days` up to 90 the loop awaits the executor many times, and the env var is read live, so an operator flipping it mid-request is exactly the case the switch exists for. When it trips, the exception comes from `intake` after the round's clock and `daysOverdue` increments, with some invoices already ticked. The caller gets a 503 with no decisions, but the grimoire and outbox keep what was already done and invoice ages are one day ahead of their ticks. State stays usable, but "no tick was processed" in the error message is then not strictly true.

```
POST /api/events -> route pre-check (503) -> host.advanceClock
                                               check -> [per round: clock++, per invoice: intake check -> executor]
```

The override is stored on the host instance. `resetHost` constructs a fresh host, so any `setEngineEnabled(false)` is gone after `/api/reset` or `/api/fixtures`, and the app reverts to the env var. The env var path is unaffected. Only embedders and tests use the override, so this is low severity, but it is a way to re-enable the engine unintentionally.

Undo and reads remain available while off (asserted by the fourth Deadbeat test). That is a sensible choice, since undo retracts effects rather than producing them, but it is a policy that the README should state next to the 503 description.

## Per-invoice tier tracking in DeadbeatHost

Undoing an email deliberately does not re-arm the tier (the grimoire note says so), so a retracted reminder is never re-sent for that invoice. Operators should know this before relying on undo to correct a wrong send. 

## Simulate stays off live state

The simulate route builds fresh events from `simulationInvoices()` and calls the engine `simulate` with a recording stub, never touching the host, outbox or grimoire. The declared set is hard-coded to `email` and `escalate` to mirror the adapter. If the adapter gains a capability the dry run will still refuse it. It is not gated by the kill switch, which is right for a dry run, but this is untested.

## Standup pack coverage

The dry-run test checks exact event ids per curse (`s-01`, `s-07` for shipped; `s-02`, `s-04`, `s-06` for blockers; `s-06` only for the three-in-seven-days escalation), so it would fail on a change to any condition or threshold. The structural test is weaker: `JSON.stringify(c)` containing `"standup"` can be satisfied by the target `team-standup` alone. It is not a blocker because the dry run covers the behaviour.
